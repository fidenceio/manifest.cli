# Manifest CLI — Tracker

Open work for the Manifest CLI repo, as one flat list in priority order.

- **This file is the canonical open-work register for the CLI repo** (locked 2026-08-15). Audits produce *evidence and verdicts*; the work they imply is filed here under a stable `§N` ID. No audit maintains its own parallel to-do list: an audit's remediation section points back here, and its `FINDINGS.tsv` carries the owning §-ID in its `remediation` column. **Audit artifacts are deliberately untracked** (`CODEX_AUDIT_*` is gitignored, locked 2026-08-16) — they are local evidence for the run that produced them, and each locks a baseline of the tracked tree that committing its own output would invalidate. So this file is the only durable record: if a finding is not filed here, a fresh clone has no trace of it.

## IDs, priority, and the renumber of 2026-08-24

- **The ID is identity, not rank.** IDs were assigned §1…§42 at the 2026-08-24 rebuild *in priority order*, so at that moment number and rank coincided. They will not stay that way, and **that is intended**: re-prioritizing moves an item within this file and never changes its number. Priority is read from **file order plus the tier tag**, never from the number. Do not renumber to restore the coincidence — encoding two facts (identity and rank) in one field is the drift defect this repo keeps paying for.
- **Sub-items are lettered** (`§15a`, `§15b`) where one area holds several independent deliverables that share an anchor and where one change usually closes several. A sub-item is a real, citable ID.
- **Why the old `§X.Y` scheme was retired.** Its first digit encoded *provenance batch* (`§8.x` = the 2026-06-05 enterprise audit, `§9.x` = chronological filing order) — meaningless to a reader, which left the second digit as the only real identifier. The old file also carried a "do not renumber" instruction protecting inbound citations, **and the drift policy below had already destroyed that property.** Measured 2026-08-24: of **308** `§`-citations in code, tests and docs, only **63 resolved to a live item**; **245 pointed at nothing**, because every time an item shipped and was deleted its citations broke. `§5.10` alone was cited 39 times with no target. Renumbering cost 63 references to repair against 245 already broken — and "Retired IDs" at the foot of this file makes all of them resolvable for the first time. The mechanism that broke them is now filed as §20.
- **Citation format: write `TRACKER §N`, not a bare `§N`.** A bare `§X.Y` is ambiguous across documents and already collides here: `STANDARD.md §2.7` (5 sites, and that file does not exist in this repo) and a workspace document's `§1.2` share the namespace with this tracker's own retired `§1.2`. The two spellings in use for this file (`TRACKER §`, 39 sites; `CLI tracker §`, 19 sites) are themselves a small drift.

## Drift policy

- Every item names a concrete deliverable and an anchor.
- When an item ships, **delete it** from this file and **add a row to "Retired IDs"** with its subject and where it shipped. Provenance lives in the merge commit and release history; the map row is what keeps the code comments citing it readable. A *fixed* defect is not an item; the item is whatever guard keeps it from returning.
- **Before deleting, re-file anything the entry names that has not shipped** — a shipped entry can carry unshipped obligations (a sweep it called for, a decision it deferred, a guard it left to a follow-up), and deleting it whole is how the absent-input sweep vanished for a day (added 2026-08-17 after that).
- **Retire shipped items in the commit that ships them, and never after the push.** Which items a release closes is known *before* the tag exists, so it belongs in the release's own auto-commit. Doing it afterwards is what produced a `docs(tracker):` commit after every release in this history. Same for anything else this file says about a release: if it can be written before the push, write it before the push; if it can only be written after, it does not belong in this file at all (see "Release state — derive it, never record it here").
- **A finding you make by *watching* a release is new work, not release cleanup.** §68 came from reading `git push`'s output and the two redaction leaks came from reading the publish — both genuinely unknowable beforehand. File them with the next change that touches code, not as an immediate follow-up commit. The distinction that matters: correcting something the push falsified is a loop and must be designed out; recording something the push *taught* you is the next unit of work.
- **File a new item under its own tier heading, not after the entry it was discovered from.** Priority is read from file order plus the tier tag (see "IDs, priority" above), so position is load-bearing: an item appended below the section its tag names is *mis-ranked*, and this file's own resume paragraph will then describe the wrong order faithfully. §73 was filed 2026-08-29 by appending it after §69, the T3 entry it was found while reviewing — putting a T2 contract-integrity item in the T3 section. **The mistake also disguises itself as a prose problem**: it presents as "the resume paragraph forgot to mention it", and editing that paragraph would have left the item mis-ranked while making the file look consistent. Guarded by [`tests/tracker_tier_order.bats`](../tests/tracker_tier_order.bats), which fails when any item's tag does not name the section it sits in, and which refuses to classify an unreadable tag rather than skipping it.
- **A claim about whether code RUNS must be established by running it, and the item must carry the command.** Not by reading the call graph, not by a `grep` for callers — those answer a different question. §65 asserted "`detect_os` has zero callers in the product" and "settled by reading, with controls"; it was wrong, and `bash scripts/manifest-cli.sh config time` disproves it in one line. The specific method that produced the error is worth knowing because it recurs: **a `grep` for call sites that excludes the defining file also excludes that file's own load-time invocation** — the same grep produced the same wrong answer twice, three days apart. An item whose central claim has no reproduction command in it is not filed, it is guessed. **This is the cheapest guard in the file and there is no test for it** — the test is that the command is written down and the next reader runs it.
- **Do not reach for a platform explanation before reproducing on one platform.** Four authoring errors in one sitting were attributed to BSD-vs-GNU divergence; on measurement, two were plain regex bugs, one was shell quoting identical everywhere, and the fourth — "macOS awk cannot parse a multi-byte character inside a comment" — was simply false, and had been committed into a test comment as guidance. A misdiagnosis written down as a lesson is worse than no lesson, because the next reader obeys it. See §74.
- **The register decays too, not just the audits it is filed from — re-verify an item before working it, however confidently it is written.** A 2026-08-24 pass re-checked twelve open items' central claims against current code and found **three dead and a fourth carrying a wrong consequence**; §65 was later found to have a false headline it had held for five days. Confidence in the prose is not evidence, and this file's own entries are not exempt. Two specific ways a stale item is produced: filing from a *document* rather than the dispatcher (a spec is a lead about a spec), and a broken measurement, which returns a plausible wrong answer rather than an error — so run a positive control on the **measurement**, not only on the fix.
- **Anchors drift; re-verify a line number before trusting it.** Four anchors in the previous revision were stale, all corrected in this rebuild: the release commit's `git add .` is `manifest-git.sh:739` (cited twice as `:765`), `manifest_audit_apply_event` is `manifest-shared-utils.sh:571` (cited as `:524`), `_json_escape` is `:490` (cited as `:443`), and the gitleaks `fetch-depth` line is `lint.yml:70` (cited as `:46`). An anchor is a hint, not evidence.

## Blast radius — tag every item CANONICAL-ONLY, PRODUCT, or BOTH

This repo is the **canonical Manifest CLI source**: what ships from here installs onto
other people's machines and runs against repos this project never sees. So "a Manifest
bug" is two different things wearing one name, and conflating them mis-ranks work.

- **CANONICAL-ONLY** — affects only this repo and its own releases. Bounded: one repo,
  recoverable, visible to one maintainer. Example: this repo's `.gitignore` missing an
  entry the template already writes into everyone else's.
- **PRODUCT** — ships inside the released artifact and executes on third-party machines.
  Example: a docs writer that overwrites a file, a `.gitignore` template that re-includes
  a file the user's editor writes secrets into, an `rm -rf` reachable from a user-set env var.
- **BOTH** — a product defect this repo also suffers. Rank it as PRODUCT.

**A PRODUCT defect outranks a CANONICAL-ONLY one of the same apparent severity.** Two
reasons, and the second is the one that gets forgotten:

1. Blast radius is every user times every repo they manage.
2. **A shipped defect does not end when it is fixed.** It persists on every machine
   running the older binary until that user upgrades. Fixing it in version N leaves
   everyone on N-1 exposed — so *"we fixed it"* and *"our users are safe"* are different
   claims, and this file must never state the second while meaning the first. **When
   closing a PRODUCT item, record the version that fixed it, because everything below
   that version still carries it.** Live example: §25's two data-loss predicates were
   fixed in v59.5.0; every install at v59.4.3 or older still has them.

Note the asymmetry that makes CANONICAL-ONLY findings worth keeping anyway: this repo is
the product's most-used customer, so a self-application gap here is often a PRODUCT defect
that simply has not been recognised as one yet — §1(a) started as "our `.gitignore` is
missing an entry" and turned out to reverse a security decision in *any* repo.

## Status tags

- **T1** — release-blocking; absence allows lost user state, lost git history, unrecoverable partial fleet state, **or irreversible publication of a secret**. (The last clause was added 2026-08-24: a private key pushed to a public remote cannot be recovered by any local action, which is the same irreversibility the other three describe.)
- **T2** — contract integrity; absence allows the safe-by-default contract to drift or bypass.
- **T3** — coverage, audit, or docs required before declaring the v1 enterprise release done.
- **DEFER** — real value, but absence causes no safety harm at fleet-of-dozens scale.
- **CUT** — considered and rejected; kept so it doesn't reappear by accident. File a fresh item rather than reviving a cut entry verbatim if the reasoning changes.

## How this list is prioritized

Ranked by four questions, in order:

0. **Whose machine does it run on?** PRODUCT before CANONICAL-ONLY, per the blast-radius section above. This was added 2026-08-24 after the first pass ranked a `.gitignore` gap in *this* repo above a docs writer that silently rewrites files in *every user's* repo — the two had been filed as if they were the same kind of thing.
1. **Can it destroy or irreversibly publish something on a normal run?** A defect that fires unannounced inside `manifest ship` outranks one needing an unusual flag, and both outrank one needing a deliberate `-y`.
2. **Is the evidence in hand, and how cheap is the fix?** Rows settled by *reading a site* have run 17-for-17 real here; rows asserting *runtime* behaviour have run 1-for-5, with two P0s withdrawn entirely. An unreproduced runtime claim is a lead, not priced work. Where two items are equally severe, the cheaper one ranks first — §1 closes four write paths by editing a `.gitignore` and one guard.
3. **Does one change close several?** Items sharing an anchor are grouped and ranked as a group.

### Release state — derive it, never record it here

**This section deliberately holds no release facts, and that is the fix to a loop.** Tag SHAs, publish timestamps, CI conclusions, tap status and `origin/main` are each one command away, and each is falsified by the next push. Recording them made this block accrete a verification paragraph per release, and made every release need a follow-up `docs(tracker):` commit to correct the previous one — visible in the history as `2468f3e`, `e6fac0a` and `ef42cc6`. **A restatement of a fact that lives elsewhere is §36's defect, and it was sitting inside the register that exists to police it.** Rewritten 2026-08-29 to end that; guarded by [`tests/tracker_release_state.bats`](../tests/tracker_release_state.bats) so it cannot creep back.

**Verify the current release in one pass.** Each command is the authority for its own row; nothing below needs to be trusted from this file.

```bash
cat VERSION; manifest --version                          # this tree / what is installed
git status --porcelain                                   # must be empty
git rev-list --left-right --count 'HEAD...@{upstream}'   # must print two zeros
git rev-parse --short "v$(cat VERSION)"                  # tag points at HEAD?
git show --stat --oneline "v$(cat VERSION)"              # ONLY VERSION + CHANGELOG.md
git ls-tree -r --name-only HEAD | grep -c CODEX_AUDIT    # must be 0
gh release view "v$(cat VERSION)" --json isDraft,isPrerelease,publishedAt
gh run list --limit 6 --json headSha,workflowName,conclusion
```

**The upstream line was broken from the day it was written, and that is the lesson, not the typo.** It read `git rev-parse --short HEAD @{upstream}`, which fails with `fatal: Needed a single revision` — **`--short` accepts only one revision**, so the two-argument form never ran, in any shell. `git rev-parse HEAD '@{upstream}'` (no `--short`) works, and `git rev-parse --short 'main@{upstream}'` works; it is the combination that does not. It was found on 2026-08-31 by running the recipe for the first time, on the release that followed the commit which introduced it. **A verification recipe nobody executes is prose, and this file replaced recorded facts with commands precisely so the commands would be run** — so the block is now executed by [`tests/tracker_release_state.bats`](../tests/tracker_release_state.bats), which runs every `git` line in it and fails if any exits non-zero. The replacement also answers the question better: two zeros is a verdict, where two SHAs still had to be eyeballed for equality.

**Three things the commands will not tell you to care about, all learned the hard way.**

- **The release commit must contain only `VERSION` and `CHANGELOG.md`.** 31 consecutive releases carried a junk commit swept in by the bare `git add .` before §1's fix. It has held since — check it, do not assume it.
- **The CI check happens *after* publication.** The ship reports `GitHub Actions: skipped (disabled by MANIFEST_CLI_GITHUB_ACTIONS_WAIT)` and the local gate is macOS-only, so a red `bats (ubuntu-latest)` is discovered on an already-published release. That has now happened twice, the second time with shell changes riding on it. It is the argument for §68 option (i), and `gh run list` above is the manual stand-in until that lands.
- **Run the recipe against an absolute root, and re-measure before reporting a verdict.** On 2026-09-02 the first post-ship check reported the pre-ship version, the pre-ship `HEAD` and no new tag — "the ship did nothing" — while the ship's own log and the remote both said otherwise. The identical checks re-run as `git -C <absolute root>` and `cat <absolute root>/VERSION` reported the published state, and `git ls-remote --tags origin` confirmed it from a second source. **The cause was never established.** The plausible one is that a sandboxed relative read hit a snapshot rather than the live tree, but nobody reproduced it, and a diagnosis nobody reproduced is not a lesson — the countermeasure is what is durable here. It is the exact mirror of the piping trap in the lessons below: there the *log* was the liar and the git state was true; here a git read was false and the log was true. So the rule that covers both directions is that **no single surface is self-validating.** A release is verified when the working tree, the remote refs and the release API agree with each other — one of them agreeing with your expectation is not evidence.

**Standing lessons about running and trusting the suite.**

- **Run the suite with `scripts/run-tests.sh`, never a bare `bats tests/*.bats`.** bats's `#!/usr/bin/env bash` shebang resolves to whatever bash is first on `PATH`; on macOS that can be Apple's 3.2, which silently mangles `declare -A` and array subscripts into "syntax error" lines. The runner prepends Homebrew's bin and refuses outright on an unsupported bash. Pass `--no-cache` before a ship, or the TTL'd green-run cache reports a cached pass.
- **Never pipe the runner when you intend to read its verdict — redirect to a file and grep that.** Piping cost two false readings of the same suite. `run-tests.sh … | tail -25` collects **`tail`'s** exit status, not the runner's, so a run with a real failure read as `0` while the failing line had scrolled out of the captured log: **a truncated log can be a failing run wearing a passing exit code.** The milder form of the same mistake made a full 1785-test pass look like a 38-test one. Establish the size with `bats --count`, never from a run's last test number. (`run-tests.sh` uses `PIPESTATUS[0]` internally for exactly this reason.)
- **A guard can violate the rule it enforces, and it will do so in its own file first.** §56 was a file restating the version its own test forbids; §57 a control that could never pass because it named its own sentinel inline; and on 2026-08-27 §20's new citation guard became its own first offender by naming the fabricated `§999`/`§777`/`§21z` it needs to control itself. **When a guard must speak the forbidden thing, exclude it from its own jurisdiction explicitly, with the reason written down** — and assert the exclusion is exactly one path so it cannot widen into a hiding place.
- **A guard that cannot see itself reports a false green.** `git grep` reads **tracked files only**, so while that citation guard was untracked the full suite reported 1785/1785 — a green that would have turned red the instant it was committed. It was found by A/B-ing tracked against untracked, not by re-running the suite. **For any check built on `git grep`, run it once against a staged copy of itself.** The same property means a mutation test that plants its probe into an untracked file proves nothing.
- **One green full run is a sample, not a verdict**, whenever any test is timing-dependent — §64 was a 1-in-3 flake that three consecutive full runs passed by luck. Nothing in the suite currently identifies which tests those are; that sweep is §66(b).
- **`git log -S '<symbol>'` names the commit that introduced a symbol; "which working tree currently fails" does not.** Three regressions were introduced and fixed inside the v59.6.0 cycle — §49, §56, §58 — and every one surfaced only by checking an agent's "pre-existing" claim against `git log -S` rather than accepting it. "Pre-existing" from an agent's vantage point means "not mine", which is a different claim.
- **Mutation-test a fix in both directions.** A guard loosened until it matches anything is a control that cannot fail; a control that names its own sentinel is one that cannot pass. Plant the defect, watch the test go red, restore, watch it go green — and make the planted instance the *shape whose absence is being claimed*, not a shape already known to be present.

(i) is preferred and does not touch the hand-edit path, because a leftover is distinguishable from a hand edit: it matches *some* increment of the committed version exactly.
