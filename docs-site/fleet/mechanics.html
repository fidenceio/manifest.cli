Manifest CLI · Fleet

Many repos, one release. No submodules.

A fleet is a folder that lists your repositories and releases them together. Each repository carries one readable line that says which fleet releases it. Everything else follows from those two facts.

design preview · planned for v63

The two facts

1. The fleet root lists its members

manifest.fleet.tsv is a plain table: name, path, selected or benched. It is committed in the fleet root and reviewed like any other file.

2. Each repo says who releases it

One line in the repo's own manifest.config.yaml. It travels with git clone, so every machine and every checkout reads the same answer.

fleet:
  released_by: fidenceio/platform    # <github owner>/<fleet name>

What add fleet does

Adding a repo is three local writes and no network call. The line reaches origin with the repo's next release, through the same gates every release passes, so there is no extra push that can fail halfway.

What ship fleet does

The release is gated. Every check runs before anything of yours is written, and the checks decide one of three outcomes per member. A conflict stops the whole fleet before any tag exists, so there is never a half-released fleet to clean up.

Try the pre-flight rule

This is the exact decision the gate makes for one member. Change the inputs and read the outcome. "Origin's copy" means the line on the branch this fleet releases from, on every remote the member pushes to.

Scenario checks

Each card is a situation the design has to survive, the steps that happen, and the outcome the test suite asserts. The tag names the same three outcomes as the gate above.

S1 · shared library

Two products use the same library

  1. Fleet core adds lib first; the line says fidenceio/core.
  2. Fleet platform adds lib too.
  3. Both fleets ship.
releasecore tags lib.
trackplatform records lib's commit in its snapshot and never tags it. No configuration beyond the add.
S2 · first claim

The line is new and origin has none

  1. add fleet api -y writes and commits the line; nothing is pushed.
  2. Origin has never carried a line for api.
  3. You ship.
releaseOrigin has no line and no snapshot ever recorded one, so there is nothing to disagree with. The release carries the line to origin. A first claim never blocks itself.
S3 · blind race

Two fleets claim one repo without talking

  1. core adds lib and ships, so origin carries fidenceio/core.
  2. platform, out of date, adds lib too; its copy says platform.
  3. platform ships.
stopPre-flight fetches, sees core on origin, and stops before any tag: lib: origin says released by fidenceio/core, your copy says fidenceio/platform. Pull to accept it, or push a take-over commit and re-run. Without the origin check this race is still caught, but only by git rejecting the push after a local tag exists.
S4 · two machines, one fleet

Teammates build separate fleet roots

  1. Each runs init fleet in their own folder, sets fleet.name: platform and github.owner: fidenceio.
  2. Neither shares a root repo.
  3. Both add the same repos.
releaseThe fleet's identity is its name under its owner, so both roots are fidenceio/platform. Members agree. Only one can push a given release first; git's ordinary push rules handle that. A fleet with no explicit name or owner is refused when it tries to write a line, so an accidental unnamed-fleet can never claim anything.
S5 · IDE workspace

A member opened from some other folder

  1. A .code-workspace lists repos from several fleets side by side.
  2. You open api there and run manifest status, then ship repo.
releaseStatus shows Released by: fidenceio/platform. ship repo prints a notice that this repo is normally released with that fleet, then proceeds. Workspaces are views; Manifest never reads them for membership.
S6 · offline

Origin cannot be reached, or --local

  1. You ship on a train with --local.
  2. Pre-flight cannot fetch.
releaseThe gate uses your copy's line and says so: could not check origin; used your copy. In --local nothing is pushed. In a normal ship with a dead origin the final push fails and the member is reported as stranded, the same recovery path as any failed push today.
S7 · fresh clone

Clone the root on a new machine

  1. git clone the fleet root.
  2. manifest init fleet --connect -y.
releaseMembers this fleet releases are cloned and follow their branch.
trackMembers released elsewhere are cloned and checked out at the commit in the snapshot. Repos you release follow their branch; repos you only use stay at the version you shipped with.
S8 · hand-over

Move a repo to another fleet, or rename a fleet

  1. manifest add fleet api --take-over -y in the new fleet.
  2. Preview: api is released by fidenceio/old. Take over: it will be released by fidenceio/new.
releaseOne visible commit in api. The old fleet's next ship sees the new line on origin and tracks api from then on.
S9 · migration

Replace a real submodule

  1. manifest plan fleet -y finds the .gitmodules entry.
  2. manifest reconcile fleet -y --adopt-submodules --commit.
releaseThe submodule becomes an ordinary repo on a branch, the parent's gitlink and .gitmodules section are removed and committed, the roster gains a row, and the line is written.
S10 · leaving

A fleet stops releasing a repo

  1. The repo is benched in the roster.
  2. Its line still names the old fleet.
benchedA benched repo is left out of the ship and the snapshot entirely; it is neither released nor tracked. Its line keeps naming this fleet until another fleet takes it over. Nothing breaks, and status shows the stale name so a human can ask.
S11 · fork

origin is a fork, upstream is the real repo

  1. lib has two remotes: origin (your fork, no line) and upstream (released by fidenceio/core).
  2. Today a release pushes to every remote.
  3. You ship.
trackThe gate reads the line from every remote the release would push to, not just origin. Upstream names core, so lib is tracked. Reading one remote while pushing to all of them was the single worst hole the review found.
S12 · deleted line

Someone removes the line on origin

  1. A cleanup commit, or a squash merge, drops released_by from lib on origin.
  2. Another fleet ships next.
stopThe last snapshot recorded fidenceio/core for lib. "No line now" after "a line before" is a removal, not a first claim, so the gate stops and names the take-over command. The snapshot is the fleet's memory; no registry is needed.

Fleet against submodules

The difference is where the pin lives. A submodule pins a commit inside the parent's history and leaves a detached checkout behind. A fleet pins in a file and leaves every repo as a normal repo on a branch.

In plain words

fleet
A folder that lists repositories and releases them together.
fleet root
That folder. It holds the list and the snapshot, and nothing else of yours.
member
A repository on the list.
released by
The one line in a repo that names the fleet allowed to tag and publish it.
tracked
Listed by this fleet, released by another. Kept at a known version, never tagged here.
benched
On the list but switched off. Left out of the ship and the snapshot.
snapshot
The file the release writes: every member's commit at that moment.
take over
Move a repo's release to a different fleet, on purpose, with one commit.
pre-flight
The checks that run before anything is written. If one fails, nothing was changed.
